# متابعة Paribu الهندسية الهادئة

هذا الفرع لحفظ أدلة المتابعة ونقطة استئناف مهمة واحدة فقط. لا يشغّل ماسحًا أو Controller جديدًا، ولا ينشر الكود. المرجع الدائم هو `monitoring/quiet_watch_checkpoint.json`.

مهمة المتابعة الدورية: `6ad0f106fa608191a823826728c80f35`، بفحص هندسي كل ساعة وبتوقيت `Europe/Istanbul`. البوت نفسه له سلسلة GitHub Actions قائمة تستهدف نحو 600 ثانية بين الدورات. تفعيل مهمة مجدولة لا يثبت نجاح تنفيذاتها المستقبلية؛ يجب تسجيل نتائج كل دورة فعلية.

## في كل فحص

1. اقرأ نقطة الاستئناف، ثم أحدث main وطلبات السحب #45 و#46 وCI والمراجعات. افصل إصلاح الفرع عن الكود المنشور فعلًا. لا تعتمد نجاح Workflow وحده: تحقق من دخول Run scanner وPersist scanner state وحداثة سجل الحالة وINFRA_HEALTH.
2. قارن الدورات الجديدة بآخر معرف تشغيل محفوظ. احفظ التوقيت ونسخة الكود الفعلية، وcadence والحالة والفجوات و429 وBTC وأسباب الرفض والتأكيد. لا تعدّ تحديثات scanner_state تغييرات في كود الاستراتيجية.
3. تتبّع NMR وMINA وSAND وBTC، ثم RAD وALT والحالات التاريخية الموثقة عند الحاجة: اكتشاف → دفتر أوامر → أولوية ومتابعة → شمعة مغلقة جديدة → إعادة البوابات → تأكيد → READY وتسليم. ميّز الغياب بسبب السعة من الرفض السوقي ومن خلل برمجي. الارتفاع اللاحق وحده لا يثبت خطأ الرفض.
4. أثبت العطل الجديد باختبار يفشل قبل الإصلاح، ثم نفّذ أصغر تعديل واختبره على فرع منفصل. لا تكرر إصلاحًا موجودًا في PR غير مدمج، ولا تعدّل بلا عطل مثبت. راجع قيود تعليمات المستودع الحالية قبل التغيير.
5. حدّث نقطة الاستئناف عند ظهور أدلة جديدة، مع سجل محدود لآخر 100 حدث ومفاتيح تمنع إعادة التنبيه للعائق المعروف نفسه. حدّث المرجع باستخدام expected SHA، ولا تستبدل حالة أحدث بحالة قديمة.

## ضوابط ثابتة

- يبقى SHADOW_MODE=True؛ لا أوامر تداول فعلية ولا تغييرات في RSI أو ATR أو السيولة أو المخاطرة أو الحصص أو التأكيدات.
- البيانات من Paribu. لا تُرقّى الشموع المحلية الاصطناعية إلى حقيقية. سجلات الحجم صفر المنشورة من المصدر تُحفظ بوسمها، ولا تُعرض كصفقات منفذة.
- الدمج يتطلب CI ناجحًا للالتزام المراد دمجه ومراجعة أمنية مستقلة لتغييرات الكود. الاختبارات الذاتية والمراجعة الذاتية ليستا مراجعة مستقلة. غياب المراجعة في #45 عائق معروف أُبلغ به المستخدم؛ لا تكرر إخباره دون تطور.
- لا Scanner أو Controller مكررًا، ولا نقل استضافة أو تعديل مشروع SatışAsistan. إذا انقطعت السلسلة، تحقق من جميع التشغيلات النشطة والمنتظرة قبل أي استعادة مأذونة. لا تكرر طلب إطلاق غامض.
- المتابعة الهندسية لا ترسل Telegram أو توصيات اختبارية أو إشعارات روتينية. تظل توصيات البوت المؤهلة خاضعة لقواعدها القائمة. لا تُخترع توصية لاختبار الإرسال.

## إعلان الجاهزية

يلزم نجاح 24 دورة إنتاج فعلية متتالية بعد آخر إصلاح مؤثر وعلى كود وإعدادات ثابتة، مع شموع منشورة سليمة، وحفظ الحالة واستعادتها، ومتابعة تحت التزاحم وانتهاء TTL، ومنع تكرار READY، وإثبات تسليم توصية READY مؤهلة وفق القواعد، وعدم وجود عطل مثبت مفتوح أو بوابة مراجعة غير مستوفاة. أي تغيير مؤثر يعيد نافذة القبول؛ تحديث الحالة المعتاد لا يعيدها.

أرسل إخطارًا واحدًا عند تحقق الجاهزية التقنية بالأدلة، أو عند عائق حرج جديد يحتاج تدخل المستخدم أو خطر على الحالة وضوابط الحماية. خلاف ذلك التزم الصمت. لا ضمان لالتقاط كل صعود أو تحقيق ربح، ولا ادعاء بعمل الفحص الهندسي بين مواعيده.

## ملاحظات الوصول

قد يعيد GitHub Contents محتوى فارغًا لملف scanner_state.json الكبير؛ استخدم blob أو raw أو git عند التزام معلوم، ولا تصف الملف بأنه مفقود بسبب ذلك. إذا حُجب Paribu من مضيف العمل وأعيد HTML مع HTTP 200، فهذه مشكلة وصول من ذلك المضيف، وليست دليلًا على غياب شموع البورصة. استخدم فحصًا عامًا محدودًا من بيئة التشغيل المأذونة عند الحاجة، مع التوقف عند 429 وعدم إرسال رسائل أو أوامر.
